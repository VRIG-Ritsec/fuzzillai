## STAGE 2: 

During this stage, use the saved files in the folder to perform analysis using trace_v8_analysis. If you need to figure out
which flags to use, run list_v8_trace_options. Your goal is to determine the execution information regarding the TASK
based on the information returned from the DB analyzer. Specifically, figure out what the JS programs do and how they run,
then create a plan for analyzing the V8 codebase to better understand how to fix the system.

Before broader tracing, if DBAnalyzer saved a concrete crash JS artifact into the generate/runtime folder, you MUST triage the minimal d8 flags needed to reproduce the crash by calling `minimize_crash_flags`.
- Seed `candidate_flags` with any exact runtime flags recovered from DB / harness metadata when available.
- If exact runtime flags are unavailable, use the tool's default Fuzzilli-oriented flag set.
- Use crash signatures grounded in raw evidence, e.g. `"Bytecode mismatch"` for this crash class.
- Treat the tool as a flag-minimization / delta-debugging pass: its purpose is to identify the smallest reproducing subset before you spend time on heavier tracing.

You should execute d8 with tracing flags (via trace_v8_analysis and/or execute_javascript_program) before finalizing conclusions.
If a crash hash is available, you must call trace_v8_analysis for that hash before Stage 5 and include concrete evidence from its stderr/stdout output.
Your final Stage 5 answer must cite: trace_v8_analysis flags_used, return_code, and at least one raw crash line from trace output.
If you called `minimize_crash_flags`, your final Stage 5 answer must also cite:
- whether the baseline full-flag set reproduced
- the minimal reproducing flag subset (or that no subset reproduced)
- the crash-signature / return-code criteria used

CRITICAL EVIDENCE PRIORITY:
1) raw runtime artifacts (stderr, signal, fatal line, stack trace) from direct d8 execution and trace_v8_analysis
2) trace output metadata from tools
3) database summaries/aggregates

Never let database aggregate summaries override contradictory raw runtime artifacts.
If DB indicates "fake crash" but raw runtime has concrete crash evidence (signal/fatal/stack), classify as inconsistent DB state and continue analysis using raw evidence.

Do not skip stages only because the crash is synthetic; gate interpretation confidence, not execution.
